# Why bubblewrap is mandatory on Unraid (and those two `--security-opt` flags)

This document explains the single most important non-default decision in this image. If you only want it to run, the conclusion is enough; if you want to know why you cannot just copy the upstream compose file, read it through.

## Conclusion

Running DSH on Unraid (and on any other kernel that does not have Landlock enabled) requires both of the following:

1. **`bubblewrap` must be present in the image** (this image bundles it; many community images do not).
2. **The container must be started with `--security-opt seccomp=unconfined --security-opt systempaths=unconfined`** (this repo's Unraid template already writes them into `Extra Parameters`, and `compose.yaml` hard-codes them as well).

Miss the first: both legs of the sandbox are broken, and DSH's `bash` tool fails closed outright.
Miss the second: `bwrap` cannot start inside the container (`No permissions to create a new namespace` / `Can't mount proc on /proc`).

## Mechanism: DSH's sandbox has two legs

`@deepseek-ai/dsh-sandbox-local` looks for backends on Linux in a fixed order:

```js
const PLATFORM_CHAINS = { linux: ["bwrap", "landlock"], darwin: ["seatbelt"], win32: ["windows-acl"] }
```

- **First tier `bwrap`**: bundled in this image.
- **Second tier `landlock`**: the `landlock-run` binary ships with DSH, but it requires `CONFIG_SECURITY_LANDLOCK` to be compiled into the kernel. Unraid 7.3.2 (kernel `6.18.38-Unraid`) does **not** have it — the `landlock_create_ruleset` syscall returns `ENOSYS`; this is not "the LSM is disabled", the LSM does not exist at all.

So on such a host you hit this error:

```
Error: sandbox mode "workspace-write" is requested but no sandbox backend is usable on this host;
refusing to run the command unconfined. Install bubblewrap or run a Landlock-enforcing kernel (Linux),
... otherwise switch the consumer to danger-full-access.
```

Note the last sentence: the only alternative is `danger-full-access` — which amounts to **no sandbox at all, and no approvals either**. So "install bwrap" is not optional; it is the difference between having a cage and having no cage.

## Why installing bwrap alone is not enough

`bwrap` needs to create user/mount namespaces, but the container's default seccomp profile blocks `unshare`, and Docker's default `/proc` mask in turn blocks remounting procfs inside the namespace. The community has already enumerated the combinations ([runzhliu/deepseek-harness-docker#35](https://github.com/runzhliu/deepseek-harness-docker/issues/35), reported on exactly Unraid 7.3.2 + kernel 6.18.38):

| Added on top of the default security configuration | Result |
|---|---|
| bwrap installed only | `bwrap: No permissions to create a new namespace` |
| `seccomp=unconfined` | `bwrap: Can't mount proc on /proc` |
| `systempaths=unconfined` | `bwrap: No permissions to create a new namespace` |
| **Both** | **`SANDBOX_OK`** |
| Both + `cap_add: SYS_ADMIN` | `SANDBOX_OK` (no difference from the row above) |
| `cap_add: SYS_ADMIN` only | `bwrap: pivot_root: Operation not permitted` |

Two key points, so you do not go down the wrong path:

1. **`SYS_ADMIN` is neither necessary nor sufficient**. A working configuration needs no extra capability; `cap_drop: ALL`, `no-new-privileges`, a read-only root filesystem and a non-root user can all be kept. The claim floating around online that "adding SYS_ADMIN is enough" is wrong.
2. The two flags block **different things**: `seccomp` blocks the namespace syscalls; `systempaths` masks paths under `/proc`, which makes mounting procfs inside the namespace fail. So supplying only one of them does not work either.

## Cost and trade-offs

- `seccomp=unconfined` widens the syscall surface inside the container; `systempaths=unconfined` exposes some `/proc` entries (for example `/proc/sys`, though they remain unwritable without `CAP_SYS_ADMIN`).
- What you get in return is **real isolation on the inner layer**: shell commands generated by the model run inside the bwrap cage and cannot write outside the workspace.
- This is **trading a wider outer shell for an effective inner cage**. For your threat model (what is untrusted is the model-generated commands, not the host), that trade is usually worth it; but it should be an **explicit choice**, which is why we write it into the template's `Extra Parameters` and explain it in the README instead of hiding it in the image.

## How to verify your host

On Unraid (there is no docker CLI inside the DSH container, so go through `ssh unraid`):

```bash
# 1. Does the host kernel actually have Landlock?
ssh unraid 'grep -c CONFIG_SECURITY_LANDLOCK /boot/config/$(uname -r) 2>/dev/null; \
  grep -i landlock /proc/kallsyms | head -3'

# 2. Does the image ship bwrap?
ssh unraid 'docker run --rm --entrypoint bwrap ghcr.io/<owner>/dsh:latest --version'

# 3. With both security-opts, can it really create a namespace? (should print SANDBOX_OK)
ssh unraid 'docker run --rm \
  --security-opt seccomp=unconfined --security-opt systempaths=unconfined \
  --entrypoint setpriv ghcr.io/<owner>/dsh:latest \
  --reuid 1000 --regid 1000 --init-groups \
  bwrap --ro-bind / / --dev /dev --unshare-pid --proc /proc --die-with-parent \
    --tmpfs /tmp --bind /workspace /workspace -- /bin/sh -c "echo SANDBOX_OK"'
```

Verifying inside DSH (the most direct way): just have it run any command, for example "run `pwd` and list the current directory". If the sandbox is unavailable you will see the `SANDBOX_UNAVAILABLE` error above; when it is available the command returns straight away.
