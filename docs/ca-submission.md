# Submitting the template to Unraid Community Applications

**Status: listed.** The template was submitted and is live in the catalogue since 2026-10-15 (verified against the feed Community Applications actually serves: one `DSH` entry, parsed from `templates/dsh.xml` on `main`). The checklist below is kept for the next submission — a fork, a new repository, or a re-submission after the entry is ever delisted — and the step that has to be repeated after any meaningful XML change is **Validate → Scan**.

For maintainers of this repository (the same applies after a fork). **Read [ca-pitfalls.md](ca-pitfalls.md) first**: that is the pitfall list compiled from the official documentation + forum evidence, including real consequences such as "a declaration that does not match reality gets you delisted", "template changes do not flow back to machines that already installed it", and "deprecation means losing security updates". This document only covers the order of operations.

## 1. Official hard requirements (missing one leaves you stuck at the submission step)

| Requirement | Basis | Status in this repository |
|---|---|---|
| Repository **public and active** | Submit → Docs → Submission Help | ✅ |
| **OSI-approved license** at the root | Same as above | ✅ MIT |
| **`ca_profile.xml` at the root with a non-empty `<Profile>`** | Docs → Repository Information XML | ✅ (`<Forum>` carries the support thread) |
| Every application entry has `<Repository>` (Docker) | Docs → Repository XML Format | ✅ |
| Run **Validate → Scan** when submitting (the entry point is **`/submit/new`**), and re-run it after every meaningful XML change | Docs → Submission Help / Builder Guide | ✅ done — submitted 2026-10-15, entry live; re-run the flow after every meaningful XML change |
| Repository layout matches the official recommendation: `README.md`, `LICENSE`, `.gitignore`, **`icon.svg`**, `ca_profile.xml` at the root, templates under `templates/` | Docs → Builder Guide | ✅ `icon.svg` has been added (vector, generated by `scripts/make-icon-svg.mjs`); the layout is asserted by `scripts/check-repo.mjs` |
| No leftover starter placeholder values (official wording: a placeholder icon "will be rejected by the submission process") | Docs → Builder Guide | ✅ `check-repo.mjs` scans for placeholder values such as `YOUR_GITHUB_USERNAME`/`example-app` |

The minimum/recommended fields in the template are asserted by `scripts/check-template.mjs` (not one of Name / Repository / Category / Icon / Overview / Project / Support / TemplateURL may be empty, volume and Config paths must match, the sandbox parameters must be in place), and **the validate workflow and every release asset build run it**.

> The old route `selfhosters/unRAID-CA-templates` no longer accepts new templates (the original wording in its PR template: *"We are no longer accepting new proposals"*), so do not spend time there.

## 2. Local verification before submitting

```bash
# 0. Repository layout + placeholder scan (against the Builder Guide)
node scripts/check-repo.mjs

# 1. Template self-check (including the CA requirements)
node scripts/check-template.mjs templates/dsh.xml

# 2. Image is anonymously pullable (must succeed when not logged in)
docker pull ghcr.io/<owner>/dsh:latest

# 3. The template installs
#    Unraid: Docker → Add Container → paste the contents of templates/dsh.xml (or import dsh.xml from the release assets)
#    After installing, confirm: the Web UI opens, /data and /workspace persist,
#             and a command run inside DSH does not report SANDBOX_UNAVAILABLE (sandbox usable, see unraid-sandbox.md)
```

## 3. Open a forum support thread (CA's requirement for self-maintained containers)

Both CA and the template guide require: **a container you maintain yourself must have an Unraid forum support thread**, and `<Support>` must point to it rather than to GitHub Issues. The support thread must at least make clear:

- what this application is, where the image is, and how to upgrade (this repository tracks versions automatically, users only need to force update);
- **why those two `--security-opt` are needed** (the Unraid kernel has no Landlock → bubblewrap is the only usable sandbox layer; see [unraid-sandbox.md](unraid-sandbox.md)) — this is the point reviewers and users are most likely to press on;
- known limitations (upstream is still pre-release and `:latest` follows the newest version; the built-in password gate has no 2FA/audit, and if you need those, set `AUTH_MODE` to `none` and hand it to SSO);
- **secure by default**: with nothing configured, what you install still comes with a password (`AUTH_MODE=builtin` + a password generated on first start and printed once), so you never end up with "a freshly installed, unauthenticated web UI that executes commands"; this is the answer if CA review asks.
- troubleshooting entry points (`/healthz`; the first lines of the entrypoint in the container log state the mode and the startup result).

Once it is open, fill in the two URLs:

```xml
<!-- templates/dsh.xml -->
<Support>https://forums.unraid.net/topic/<thread ID>/</Support>
```
```xml
<!-- ca_profile.xml -->
<Forum>https://forums.unraid.net/topic/<thread ID>/</Forum>
```

## 4. Submitting in the CA interface

The **Submit** workspace at `ca.unraid.net`: enter the repository address → **Validate** (parses the XML) → **Scan** (duplicate-application and requirement checks) → preview the listing → submit. **Re-run it after every meaningful XML change**; the parser regenerates the feed entry from the latest template.

The "prove repository ownership" step requires you to place a `.unraid/community-apps-claim.json` in the repository — **it is not a secret**, it holds only a public nonce and a claim code, generated by that flow and then committed to the repository. This repository deliberately does not contain this file: you have to go through the flow once yourself to get the one that corresponds to your own account.

## 6. Afterwards, on every upstream release

`.github/workflows/release.yml` checks npm every day for the highest version of `@deepseek-ai/dsh` (including alpha/rc); when there is a new version it builds, smoke-tests and pushes the image, and generates a **version-locked** template XML as a release asset. What users see in CA is always `:latest`; anyone who wants reproducibility can use the locked-version template from the release assets.

## Icon hosting: why not to use a raw link

Measured (China mainland home broadband egress):

| URL form | Result |
|---|---|
| `raw.githubusercontent.com/...` | **timeout** |
| `cdn.jsdelivr.net/gh/...` | **timeout** |
| `github.com/<owner>/<repo>/raw/...` | 302 redirect to raw (the browser then times out the same way) |
| `ghproxy.net/https://raw.githubusercontent.com/...` | 200, about 1.0–1.9 s |
| **`gh-proxy.com/https://raw.githubusercontent.com/...`** | **200, about 0.2 s** |
| own domain | 200 |

The bytes returned by the proxy were compared by sha256 against the authoritative copy fetched directly through the API (they match); it is not just "it opens". If the proxy stops working one day: just switch `<Icon>` to hosting on your own domain or another proxy; **a broken icon image does not affect installation**.
